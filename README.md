# travel-agency — «Умное турагентство» на мультиагентной системе

Мультиагентная система (MAS) на **LangGraph / LangChain 1.x**, которая по запросу вида
«Спланируй отпуск в Токио на 5 дней в марте, найди билеты и отель» собирает маршрут по дням,
подбирает рейсы и отели и бронирует их — **только после явного подтверждения человеком**
(Human-in-the-Loop).

---

## Почему здесь нужна MAS, а не один агент

Если отдать одному агенту все девять инструментов (поиск рейсов, отелей, достопримечательностей,
бронирование, отмена), он начинает путаться в вызовах и галлюцинировать: контекст забивается
выдачей поиска, а описания инструментов конкурируют между собой.

Решение — **изоляция контекста**: каждый саб-агент видит только свои 2–3 тула и свой системный
промпт, а супервизор оперирует не сырыми данными, а короткими результатами делегирования.
Побочный, но важный эффект: опасные инструменты (`book_flight`, `book_hotel`, `cancel_booking`)
физически недоступны супервизору — он не может вызвать их «в обход» владельца.

## Архитектура

```
              ┌──────────────────────────────┐
   запрос ───►│  supervisor (оркестратор)    │  ← единственный checkpointer
              │  tools = 4 саб-агента        │
              └───┬───────┬───────┬──────┬───┘
                  │       │       │      │
   plan_destination   handle_flights  handle_hotels  handle_support
        │                  │              │              │
  search_attractions   search_flights  search_hotels  cancel_booking ⏸
  get_attraction_...   get_flight_...  get_hotel_...
                       book_flight ⏸   book_hotel  ⏸

                                     ⏸ = interrupt, ждёт решения человека
```

### Агенты

| Агент | Роль | Инструменты | HITL |
|---|---|---|---|
| `supervisor` | Разбивает запрос на подзадачи и делегирует | 4 саб-агента, обёрнутых в тулы | — |
| `destination` | Достопримечательности, маршрут по дням | `search_attractions`, `get_attraction_details` | нет |
| `flights` | Подбор и бронирование рейса | `search_flights`, `get_flight_details`, `book_flight` | на `book_flight` |
| `hotels` | Подбор и бронирование отеля | `search_hotels`, `get_hotel_details`, `book_hotel` | на `book_hotel` |
| `support` | Отмена брони по PNR | `cancel_booking` | `approve` / `reject` |

### Три правила сборки

1. **Саб-агент как тул.** Каждый агент оборачивается в `@tool`, который принимает строку-запрос
   и возвращает текст последнего сообщения. Супервизор общается с воркерами через узкий
   текстовый интерфейс, а не через общий стейт — это и есть изоляция контекста.
2. **HITL вешается на владельца опасного тула**, а не на супервизор.
   `HumanInTheLoopMiddleware(interrupt_on={...})` живёт внутри `flights` / `hotels` / `support`.
   Поисковые тулы помечены `False` — дёргать человека на чтении данных бессмысленно.
3. **`checkpointer` только у супервизора.** Прерывание из вложенного графа всплывает наверх само,
   а состояние треда сохраняется в одном месте. У саб-агентов своего чекпоинтера нет.

### Цикл HITL

```python
config = {"configurable": {"thread_id": "trip-001"}}

result = supervisor.invoke({"messages": [{"role": "user", "content": "..."}]}, config)

if result.get("__interrupt__"):          # агент дошёл до book_flight и остановился
    for intr in result["__interrupt__"]:
        for req in intr.value:           # по одному запросу на tool-call
            print(req)                   # показываем человеку, что именно будет забронировано

    result = supervisor.invoke(
        Command(resume={"decisions": [{"type": "approve"}]}),
        config,
    )
```

До решения человека бронирование **не выполняется**; после `approve` — выполняется ровно один раз
(см. идемпотентность ниже).

## Mock-API (`src/travel_agency/tools/`)

Чистый Python без LLM — модули тестируются и мокаются отдельно от агентов.
LangChain-обёртки создаются лениво фабрикой `langchain_tools()`.

- **`flights.py`** — рейсы Москва / Амстердам → Токио, март 2026. Из Москвы прямых нет (только
  стыковки через DXB, IST, PEK, AUH), из Амстердама есть прямые KLM. Цены и время в пути
  откалиброваны под реальные порядки величин. Один рейс намеренно sold-out — для проверки
  обработки ошибок бронирования.
- **`hotels.py`** — 13 отелей Токио с координатами, районами, рейтингом и ценами. Одна запись
  «отравлена» prompt-инъекцией в описании (включена по умолчанию — так проверяется guardrail;
  отключается `TRAVEL_SAFE_MODE=1`). Ещё одна врёт в описании: заявлен люкс, а на фото хостел.
- **`attractions.py`** — 4 города (Токио / Амстердам / Париж / Москва), 18 записей по Токио
  с районами, длительностью визита, часами работы и тегами (`museum`, `kids`, `vegetarian_food`,
  `rain_ok`) для фильтрации под профиль пользователя.
- **`booking.py`** — бронирование с Pydantic-валидацией аргументов, типизированными исключениями
  (`FlightNotFound`, `SoldOut`, `InvalidDates`), **идемпотентностью по `idempotency_key`**
  и детерминированным PNR (хэш от ключа → воспроизводимые тесты).

> **Про идемпотентность.** При `resume` LangGraph перезапускает прерванный tool-call целиком,
> поэтому наивный `book_flight` списал бы место дважды. `idempotency_key` делает повторный вызов
> безопасным: тот же ключ → та же бронь, без второго списания.

## Запуск

Нужен Python ≥ 3.10 и [uv](https://docs.astral.sh/uv/).

```bash
git clone https://github.com/volzock/travel-agency.git
cd travel-agency
uv sync
```

Создайте `.env` в корне:

```env
BASE_URL=https://api.your-provider.com/v1   # любой OpenAI-совместимый endpoint
API_KEY=sk-...
MODEL=your-model-name
MEM0_API_KEY=...                            # проверяется на старте, см. ниже
```

`Environment` валидирует переменные при импорте и падает с `KeyError`, если чего-то не хватает.
`MEM0_API_KEY` сейчас только проверяется — долговременная память ещё не подключена, но переменная
обязательна.

Дальше — `src/travel_agency/mas/MAS.ipynb`: первая ячейка переходит в корень репозитория,
остальные собирают агентов и прогоняют сценарий с бронированием и подтверждением.

## Что дальше

- Долговременная память профиля через `mem0` (предпочтения пользователя между сессиями).
- Guardrail на prompt-инъекции в выдаче тулов — «отравленный» отель для этого уже лежит в моках.
- Агент-критик, проверяющий план по фактическому чек-листу (цена, район, необходимость
  предварительного бронирования).
- Замена mock-API на живой поиск (`ddgs` + `playwright` + `trafilatura` уже в зависимостях).
- Персистентный чекпоинтер (SQLite/Postgres) вместо `InMemorySaver`.

## Ограничения

Учебный проект. Данные о рейсах, отелях и достопримечательностях — синтетические, бронирования
живут в памяти процесса. Сборка MAS находится в ноутбуке, а не в виде сервиса; автотестов пока нет.
